# 02 데이터 저장 — 정기보고서 원문 DB `dart_periodic`

## 왜 별도 DB인가
정기보고서(사업·반기·분기)는 이 케이스만 쓰는 재료가 아니다. 그래서 프로젝트 이름이 아니라
**문서 종류 이름의 DB**에 둔다. 다른 케이스도 같은 테이블을 채우고 읽는다.

## 규약 — `ipo_db.cf_filing*` (ipo_registration/commitment_followup s03·s04) 그대로
- 목록은 `list.json` 직접 호출, `pblntf_ty='A'`, `last_reprt_at='N'`(정정본·원본 모두 보존).
- `doc_class` = annual · semi · quarter · other. 보고서명 접두어를 뗀 뒤 `^사업보고서\s*\(` 처럼 앵커로 판정
  (부분 일치 금지 — "사업보고서제출기한연장신고서" 오분류 실측).
- `period_end` = 보고서명 "(2026.06)" 의 말일. `rev_kind` = original · content([기재정정]) · attach([첨부추가]·[첨부정정]).
- 원문은 `document.xml` ZIP의 **모든 파일**을 `file_seq` 로, UTF-8 정규화 후 gzip(`body_gz`).
- status 014 는 오류가 아니라 상태(`xml_status='missing'`) → HTML 트랙.
- 본문 버전(`is_body_version`)은 목록 단계에서 최신 접수로 잠정, 원문을 받은 뒤 절 제목 수로 확정.
- OpenDART 는 **IP 단위로 차단**한다. 같은 PC에서 다른 수집 세션과 동시에 돌리지 않는다. 간격 1초, 분당 100건 상한.

## 테이블

| 테이블 | 키 | 내용 |
|---|---|---|
| `pr_corp` | corp_code | DART 고유번호·종목코드·회사명 (corpCode.xml) |
| `pr_filing` | rcept_no | 정기공시 목록 + 분류·상태 (cf_filing 과 같은 열 + `stock_code`·`origin`) |
| `pr_filing_xml` | rcept_no, file_seq | 원문 gzip (cf_filing_xml 과 같은 열) |
| `pr_filing_toc` | rcept_no, toc_no | DART 뷰어 목차 노드(title·dcmNo·eleId·offset·length·dtd) — sr_filing_toc 와 같은 열 |
| `pr_fs_value` | rcept_no, fs_scope, item | 원문에서 뽑은 재무상태표 값(자본총계 등)과 위치(toc_no, 행 텍스트) |
| `pr_capture` | rcept_no, toc_no, item | 캡처 이미지 경로·뷰어 URL·캡처 시각 |

`origin` 열: `opendart`(이 파이프라인이 받음) · `ipo_db.cf_filing`(기존 수집분을 복사).

## 기존 수집분 재사용
| 위치 | 내용 | 처리 |
|---|---|---|
| `ipo_db.cf_filing` / `cf_filing_xml` | 신규상장 96사 정기보고서 479건 (2024.11~2026.08), gzip 원문 | 같은 rcept_no 를 `pr_filing`·`pr_filing_xml` 로 복사(`origin='ipo_db.cf_filing'`), 다시 받지 않는다 |
| `holding_shares/exports/dart/raw/*.txt` | 사업보고서 등 125건, 평문 텍스트(목차·XML 구조 없음) | 목차 위치를 못 만들어 원문 저장소로는 쓰지 않는다. 숫자 대조용 참고만 |

## 다시 받지 않는 원칙
- 모든 수집 스크립트는 `pr_filing.xml_status IS NULL` 인 것만 받는다. 재실행해도 받은 것은 건너뛴다.
- CHECK 게이트웨이 응답은 `data/raw/gw/` 에 요청 해시로 캐시한다.
